# WhatsApp Transcription Bot

WhatsApp bot that automatically transcribes received voice messages. The system runs inside a Docker container, connects to WhatsApp using the native Multi-Device protocol (no browser involved), and uses Google servers for speech transcription.

The project idea was born based on this repository: <br>
https://github.com/puluceno/WhatsappTranscriptionOffline <br>
Almost all the code was generated by AI (DeepSeek and Claude); I mostly acted as a tester for debugging and orchestrated the work.

---

## Overview

This project implements a WhatsApp bot that listens for incoming voice messages, converts them to the appropriate audio format, and transcribes them using speech recognition services. The transcription is then sent back as a reply to the original message.

---

## System Architecture

### Operating System

- **Ubuntu 22.04 LTS (Jammy Jellyfish)** - Stable, long-term supported Linux distribution

### Main Components

The container includes three main components that cooperate with each other:

**1. WhatsApp Client (Node.js)**

- File: `index.js`
- Library: `@whiskeysockets/baileys`
- Purpose: connects directly to WhatsApp's native Multi-Device WebSocket protocol, receives messages, and handles the QR code. No browser or DOM automation: the library speaks the protocol directly.

**2. Transcription Server (Python)**

- File: `server/app.py`
- Framework: FastAPI with Uvicorn
- Purpose: Receives audio files, sends them to Google servers for transcription, adds punctuation

**3. Process Manager (Supervisord)**

- File: `supervisord.conf`
- Purpose: Starts and monitors Node.js and Python processes, restarts them in case of crash

## Project Structure

```
WhatsappTranscription/
├── docker-compose.yml          # Docker Compose config (uses env_file, bind mounts source code)
├── Dockerfile                  # Container definition
├── docker-entrypoint.sh        # Startup script
├── supervisord.conf            # Supervisor config (runs Node and Python)
├── .env                        # Environment variables (loaded via env_file)
├── .dockerignore               # Build exclusions
├── .gitignore                  # Git exclusions
├── .gitattributes              # Forces LF line endings on files executed inside the container
├── package.json                # Node.js dependencies
├── index.js                    # WhatsApp bot with group exclusion support
├── README.md                   # This file
├── README_it.md                # README.md translated in Italian
├── server/
│   ├── app.py                  # FastAPI transcription server
│   └── requirements.txt        # Python dependencies
└── Volumes/                    # Persistent data (session, models, cache)
    ├── session_data/           # Baileys session (Multi-Device credentials, in baileys_auth/)
    └── cache/                  # Hugging Face model cache (punctuation model, ~2 GB)
```

> **Note:**  All folders under `Volumes/` are mounted as Docker volumes to specific container paths. This keeps critical data (session, models, cache) directly on the Windows filesystem, avoiding uncontrolled growth of the WSL2 VHDX file.  
The entire project directory (excluding `node_modules`) is bind-mounted to `/app` inside the container. This allows you to edit source files (`.env`, `index.js`, `server/app.py`, etc.) and apply changes by simply restarting the container with `docker-compose restart`. No rebuild is needed unless you modify `package.json` or `requirements.txt`.  
Temporary audio files live in `/tmp`, mounted as `tmpfs`: they stay in RAM and never touch disk.

## Configuration

### Environment Variables

The `.env` file exposes the following variables:

| Variable | Default | Description |
|---|---|---|
| `PATH_AUDIO` | `/tmp` | Folder for temporary audio files (mounted as `tmpfs`, i.e. in RAM) |
| `SESSION_PATH` | `/app/session_data/baileys_auth` | Folder where Baileys stores the Multi-Device session credentials |
| `TRANSCRIBE_URL` | `http://127.0.0.1:8000/transcribe` | Internal endpoint of the Python transcription server |
| `TRANSCRIBE_TIMEOUT_MS` | `180000` | HTTP request timeout towards the transcription server |
| `GROUPS` | `*` | `*` = all groups enabled for transcription; otherwise a comma-separated list of IDs |
| `EXCLUDED_GROUPS` | *(empty)* | Comma-separated list of group IDs excluded from transcription |
| `SHOW_CHAT_IDS` | `false` | `true` to show real chat IDs in the logs (needed to populate `EXCLUDED_GROUPS`) |
| `TRANSCRIBE_OWN_MESSAGES` | `true` | Also transcribes voice messages sent from the number linked to the bot |
| `ONLY_PTT` | `false` | `true` = transcribe only voice notes; `false` = also attached audio files |
| `MAX_AUDIO_SECONDS` | `0` | Ignores audio longer than N seconds (`0` = no limit) |
| `MARK_AS_READ` | `false` | Marks voice messages as read after transcription |
| `BAILEYS_LOG_LEVEL` | `silent` | Verbosity of Baileys' internal logger (`silent`, `error`, `warn`, `info`, `debug`, `trace`) |
| `TZ` | `Europe/Rome` | Container timezone |

### Excluding a group from transcription

1. **Temporarily enable ID display**  
   Edit the `.env` file and set `SHOW_CHAT_IDS=true`.  
   Then restart the container:  
   ```bash
   docker-compose restart
   ```

2. **Find the group ID**  
   Send any voice message in the group you want to exclude.  
   In the container logs (`docker-compose logs -f`), you will see a line like:  
   ```
   2026-07-27T12:34:56+02:00|group| (audio ricevuto) - Chat ID: 393345872509-1442996558@g.us - ptt=true - durata dichiarata=7s
   ```  
   The part `393345872509-1442996558@g.us` (or one ending with `@lid`) is the group ID. Copy it exactly as-is: it is the JID assigned by WhatsApp's servers and never changes over the lifetime of the group, regardless of its name, admins, or participants.

3. **Set the exclusion**  
   Open `.env` again and add the ID to `EXCLUDED_GROUPS`. For example:  
   ```
   EXCLUDED_GROUPS=393345872509-1442996558@g.us
   ```
   To exclude multiple groups, separate them with commas:  
   ```
   EXCLUDED_GROUPS=id1@g.us,id2@g.us
   ```

4. **Restart the container**  
   After editing `.env`, restart the container:  
   ```bash
   docker-compose restart
   ```

5. **(Optional) Hide IDs again**  
   If you prefer not to show real IDs in logs, set `SHOW_CHAT_IDS=false` in `.env` and restart the container once more.

## How It Works

### Processing Flow

1. **Reception**: The bot receives the incoming message event from WhatsApp
2. **Filter**: Before downloading anything, checks whether the message is a voice note/audio and whether the chat is enabled for transcription
3. **Download**: If the message passes the filter, downloads the audio buffer directly from WhatsApp's servers (no browser involved)
4. **Conversion**: Converts to 16 kHz mono WAV with ffmpeg
5. **Send to Google**: The Python server sends the audio file to Google Speech Recognition servers
6. **Receive transcription**: Receives the transcribed text from Google servers
7. **Punctuation**: Adds punctuation with a local NLP model
8. **Reply**: Sends the transcription as a quoted reply to the original message
9. **Cleanup**: Deletes temporary files (which in any case only ever lived in RAM, since `/tmp` is a `tmpfs`)

### Privacy and Security

**Warning**: Audio files are sent to Google servers for transcription.

- No permanent storage of audio files in the container: they live only in RAM (`/tmp` as `tmpfs`) and are deleted after processing
- No logging of transcriptions
- Logs contain only technical information (duration, timings, chat IDs if `SHOW_CHAT_IDS=true`)
- The WhatsApp session (Multi-Device credentials) is saved locally in the `Volumes/session_data/baileys_auth/` folder
- The client connects directly to the WhatsApp protocol and never goes through a browser or WhatsApp Web

> **Note**: Baileys is not an official WhatsApp/Meta library, but a reverse-engineered implementation of the Multi-Device protocol. It's more stable than the old browser-based automation, but it remains an unauthorized client: use it with a number you wouldn't mind losing access to, and avoid bulk sending.

## Optimizations and Maintenance

### Disk Growth Control

To prevent the WSL2 VHDX file from growing indefinitely, the following measures have been adopted:

- Windows volumes: the directories that accumulate data (`session_data`, model cache) are mounted to Windows folders via `./Volumes/`.
- Files in `/tmp` older than 60 minutes are deleted every hour.
- Every 24 hours, Hugging Face temporary files not accessed for 30 days (e.g., `.lock` files) are removed while preserving main models.
- Docker log rotation: `docker-compose.yml` is configured with a limit of 3 log files of 100 MB each.
- VHDX size limit: Create (or modify) the file `%UserProfile%\.wslconfig` with the following content at the top:

```
[wsl2]
defaultVhdSize=20GB
```

### Shrink VHDX File

After starting and configuring the container, you can reclaim disk space by compacting the Docker distro VHDX using these commands

```bash
docker system prune -a -f --volumes

docker builder prune -a -f
```

Close Docker from the TrayBar

```bash
wsl --shutdown

diskpart

select vdisk file="%LocalAppData%\Docker\wsl\disk\docker_data.vhdx"

attach vdisk readonly

compact vdisk

detach vdisk

exit
```
